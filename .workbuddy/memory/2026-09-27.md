## 修复：下载期间文件列表闪烁 + 部分行显示不出来（master 实测上报）

**根因链（全部代码实证）**：
1. 下载中 `downloadManager.ensurePolling()` 每 **1000ms** 轮询原生状态（downloadManager.js:215）。
2. `pollProgress()` 有字节变化就 `notify()` → `getAllTasks()` 返回**新数组**，即使 task 对象引用不变。
3. `FileTransferModal.jsx` 的订阅 `setDownloadTasks(tasks.filter(...))` 每秒触发一次 setState（filter 必然产生新数组），且弹窗当时**未对行组件做 memo**。
4. 弹窗一次渲染整个目录的全部条目（master 那次是 **405 项**，无虚拟化/分页），行内还有 IIFE + 多层 class + `animate-spin`，整体又在 `backdrop-blur-xl` 下 → Android WebView 每秒全量 reconcile + 样式重算 + 重栅格化 → 肉眼看到闪烁；滚动时掉帧就出现「空白行」。

**修法**：
- 把 `formatSize/formatDate/getFileIcon` 提升到模块级（保持行为一致）。
- 行抽成 `React.memo` 的 `FileRow`，**传原始值**（`taskId/taskStatus/taskProgress`）而不是 task 对象——因为 downloadManager **原地修改** task 对象（`task.progress = ...`），传对象引用会让 memo 永远判等、UI 卡旧状态。
- 回调稳定化：`toggleSelect` 改 `useCallback`；`handleDownload` 用 ref 转发成 `stableDownload`；`stableOpenDir` 用 `useCallback`。
- 订阅加**签名短路**：`id:status:progress:bytes` 串比对，无变化直接 return，连父组件重渲染都省掉（如 statusMessage 跳动、其他游戏任务）。
- `UploadModal.jsx` 同样加上传订阅的签名短路（原生每块 16MB 完成即 emit，局域网约 3~5 次/秒）。
- 结果：下载进度每秒更新现在**只影响真正在下载的那一行**。

**复核方式**：`npx vite build` → `NODE_OPTIONS= npx cap sync android` → `gradlew :app:assembleDebug`，并用 python zipfile 打开 APK 校验 `assets/public/assets/index-*.js` 里含本次新增文案（gradle 秒回 SUCCESSFUL 不代表资源已换）。

## 四条 master 实测反馈修复（同一轮）

### ① 上传假「已完成」：Capacitor getLong 陷阱（**重大，两个现象同一个根因**）
- **症状**：客户端显示"已完成/上传完成，PC 端已收到"，但 PC 上只有 `<文件名>.<ticket>.part` 且**恒为 0 字节**；票据一直挂在 `upload_state.json` 里（30 分钟后才过期，且期间占满并发上限 → 后续上传报 429「上传任务已满」）。
- **根因（已读 Capacitor 源码确认）**：`PluginCall.getLong(name, default)` 的实现是
  `Object v = data.opt(name); if (v instanceof Long) return (Long) v; return defaultValue;`
  —— **只认 Long**。JS 传来的普通整数经 JSON 解析成 **Integer**（只有超出 int 范围才是 Long），于是 `fileSize` **静默变成默认值 0**。
  原生 `while (receivedBytes < fileSize)` 一次都不执行 → 直接 `notifyCompleted` → 假完成。**只有小文件中招，大文件反而正常**（数字超 int 范围被解析成 Long）。
- **修法**：插件改用 `call.getData().opt(...)` + 自写 `toLong(Object)`（Number/String 都能转）；`UploadService.doUpload` 开头加 `fileSize<=0` 防御，报「文件大小无效」而不是假完成。
- **顺带加固（端到端确认）**：完成判定改为**只认服务端**——末块 PUT 响应必须带 `status:"completed"`（服务端 rename 成功后才回）；否则客户端主动调新增的 `POST /api/uploads/:ticket/complete`（幂等）请求收尾，仍失败则报暂停+原因。
  服务端 `finalizeTicket()` 抽成幂等函数；已完成票据**保留 10 分钟**（`COMPLETED_TTL_MS`）再清理，否则末块响应丢包时 `/complete` 会拿 404 被误判失效；`cancelTicket` 对已完成票据**拒绝删除**（迟到取消不能删已完成的文件）。
- 测试：`test_uploader.js` 加 T14（未收满收尾 409 / 末块带 completed / 完成后 GET 仍 completed / 重复收尾幂等 / 迟到取消不删文件）→ **53/53 全过**。

## 修复：删了半成品仍报「上传任务已满」（master 实测上报）

**症状**：master 删掉两个没传完的文件后，移动端仍一直 429「上传任务已满」。

**实证**：`%APPDATA%\gamemanage\uploads\upload_state.json` 里那两张票据创建于 10:18:38 / 10:19:31，`expiresAt` 为 10:48:38 / 10:49:31；到 11:13 已过期 24 分钟，**仍占满 2 个并发额度**。

**三条根因（都是设计漏洞，不是偶发）**：
1. `loadPersistedState()` **不校验 `expiresAt`** → 重启后把过期票据原样读回内存当 `uploading`，白占额度。
2. 首发释放时机太晚：只有 5 分钟清理循环（`setInterval` 首次执行要等 5 分钟）＋ 各入口的懒清理（分块 PUT / GET 状态），而 **`createTicket` 自己不做任何清理**。
3. 并发计数只看 `status==='uploading'`，**不看磁盘上还有没有凭据** → 用户手动删掉 `.part` 后，票据照样占额度直到过期。

**修法（三层）**：
- 新增 `isTicketActive(t)`：并发计数的**唯一依据** = 状态在传(含 finalizing) && 未过期 && (磁盘有 `.part` 或正式文件 || 距 `createdAt` 未超 `TICKET_STALE_GRACE_MS`=2min 宽限期)。宽限期专防「刚申请、第一块还没落盘」被误判。
- `createTicket`：**先 `cleanupExpired()` 再计数**（额度即时归还，绝不等 5 分钟）；`cleanupExpired` 里对「未过期但磁盘无凭据」的票据新增 `stale-released` 分支清理；补上 `finalizing` 过期分支（原先该状态过期后永不清理，会永久占额度）。
- `loadPersistedState`：丢弃过期票据并 `persistState()` 落盘清除（`state-pruned-on-load`）。
- `main.js`：启动时 `loadPersistedState()` 后**立即 `cleanupExpired()`**（原先要等 5 分钟循环首次执行，表现为「重启后头 5 分钟一直提示已满」）。顺带去掉重复的 `sweepOrphanParts`（已含在 cleanupExpired 内）。

**验证**：`test_uploader.js` 新增 T0（12 条）→ **65/65 通过**。覆盖：过期票据不载入、过期项落盘清除、`isTicketActive` 四态语义（含「磁盘仍有 .part → 不误放额度」）、僵死票据被申请流程即时清理（用两张 `ghost` 票据占满额度来锁定这个 bug）。

## 大库（4T）游戏库主列表性能优化（master 点名要求现在就改）

**触发**：master 指出「GameCard 也是 glass-panel，每张卡一个 blur，库大了会犯同样的病 —— 现在就改，我有的库有 4T」。

**查出来 4 条问题，比预想的严重**（前两条才是大头，blur 反而是最小的）：

1. **`preloadCovers` 全量预热封面（最致命）**：App.jsx 调用时**没传 limit**（`limit` 默认 0 = 不限量），于是 `syncOfflineCache` 把**所有带封面的游戏**在 6 并发下全拉一遍并写 IndexedDB。数千款 → 持续几十分钟占满网络 + 海量写入；且 `onProgress` 每张封面都 `setCacheProgress` → App 高频重渲染，而 GameCard 没有 memo → 40+ 张卡全量重渲（每张还带 blur 层）。
2. **GameCard 每卡多个模糊合成层**：外层 `glass-panel`(blur 16px) + grid2 每个标签 `backdrop-blur-md`（最多 3 个）+ grid3 标题栏 `backdrop-blur-md` → 40 卡最多约 160 个合成层。
3. **GameCard 无 memo，且父组件传内联箭头回调** `onClick={(item) => setSelectedGame(item)}` —— 每次渲染都是新引用，就算加了 memo 也全失效。
4. **无限滚动无渲染上限**：滚到几百项后，所有屏外卡片仍参与布局与合成（缺 `content-visibility`）。

**修法（四层）**：
- `index.css` 新增三个工具类：`.cv-auto`(320px，双列)/`.cv-auto-grid3`(210px)/`.cv-auto-list`(96px) = `content-visibility:auto` + `contain-intrinsic-size:auto <估算值>`（`auto` 关键字让浏览器记住实测高度，滚动条不跳动；估算值按各模式实际卡片高给，避免首滚位置跳动）。
- `GameCard.jsx`：`glass-panel` → `bg-slate-900/75`（与原 `rgba(15,23,42,.75)` 视觉等价）、去掉标签与标题栏的 `backdrop-blur-md`、`transition-all` → `transition-colors`、按模式挂上对应 cv-auto 类；导出改为 `React.memo(GameCard, arePropsEqual)`，比较函数**只比对卡片真正用到的字段**（id/name/alias/pinned/hasCover/coverUrl/updatedAt/tags + viewMode + onSelect）。
- `App.jsx`：GameCard 的 `onClick` prop 改名 `onSelect`，传 **`setSelectedGame`**（useState setter 引用恒定 → memo 才能真正生效）。
- **封面预热改两阶段**：`preloadCovers(..., limit=COVER_PRELOAD_PRIORITY=150)` 只等首屏这批（进度条只反映它 → 列表秒开）；其余交给新增的 `startBackgroundCoverFill`（并发 2 + 每张 80ms 主动让出主线程 + `bgCoverFillRef` 可被下一轮同步打断 + 组件卸载时取消）。单张预热逻辑抽成 `cacheStorage.preloadOneCover()` 供两条路径共用。
- **切片语义必须对齐**：`startBackgroundCoverFill` 内是「先 `filter(g=>g.hasCover)` 再 `slice(skipCount)`」，与 `preloadCovers` 内部（先滤后取前 N）完全一致；若改成直接 `list.slice(150)`，调整优先级常量时就会漏网或重复。
- `CoverImage.jsx`：blob LRU 缓存 35 → 100（大库快速滚动时窗口过小会让屏外封面反复 revoke/createObjectURL 抖动；100×20KB≈2MB 可忽略）；`<img>` 增加 `decoding="async"`。

## 修复：设置页「保存并重启 API 服务」卡住不响应（master 实测上报）

**症状**：PC 端勾选「允许移动端上传」→ 点「保存并重启 API 服务」→ 界面卡在「保存中…」**永不恢复**，只能手动退出设置页或退出应用。

**根因（30 行测试脚本在真实运行时复现，非推断）**：

`stopApiServer()` 只写了 `server.close(cb)`。Node 的 `close()` 回调要等**所有已建立连接**关闭才触发，而它**自己不会去关**已建立的连接：
- 本机 Electron **28.3.3 内置 Node 18.18.2**；`server.close()` 在 Node 18 下**不理会 idle 的 keep-alive 连接** → 回调挂住。
- 移动端 `downloadManager.js:234` 每 **3000ms** `pollProgress()` 轮询一次 → 连接被反复复用，`server.keepAliveTimeout=120000` **永远不到期** → 连接**永不 idle** → `close()` 回调**永不触发** → `await stopApiServer()` 永久 pending → IPC 不返回 → `SettingsModal` 的 `apiSaving` 永远为 true。
- **这就是「必须手动退出」的原因**：等下去也不会好（不是慢，是死等）。若移动端没在轮询、连接进入 idle，则要等满 120 秒才恢复。

**关键版本差异（差点让我误判）**：同一测试脚本在**纯 Node 22** 下，空闲连接场景旧逻辑 **1ms 就关闭**（Node 19+ 改了 `server.close()` 会一并处理 idle 连接）——所以在 Node 22 上测根本复现不出来。
**⇒ 结论：主进程行为必须在真实运行时验证**：`ELECTRON_RUN_AS_NODE=1 ./node_modules/electron/dist/electron.exe <script>`。

**修法（两层）**：

1. `main.js` 的 `stopApiServer()` 重写，加**三重保险**，绝不允许永久挂起：
   - `server.close(finish)` 后立刻 `server.closeIdleConnections()`（直接断开空闲 keep-alive 连接，最常见情形由此秒解）；
   - `API_STOP_GRACE_MS = 2000` 宽限窗口后 `server.closeAllConnections()` **强制断开**进行中的请求（上传/刷新库），再给 500ms 让 close 回调触发；
   - `settled` 标志 + `finish()` 兜底 `resolve()`，无论如何都会返回。
2. `save-api-settings` 新增 `needsRestart` 判断，**只改「免重启」项时不再重启 HTTP 服务**：
   ```js
   const needsRestart = enabled !== current.enabled || host !== current.host || port !== current.port
     || (!apiServerState.running && enabled);
   ```
   依据：`handleApiRequest` **第一行**就是 `const settings = getApiSettingsFromDb()`，`allowUpload`/`exposeFullPath`/`allowRemoteLaunch`/上传目录/大小上限全部**每请求实时读**（main.js:4619/4657 等处），保存后下一个请求立即生效，重启纯属多余。
   **⇒ 用户这个操作（只勾「允许移动端上传」）现在根本不进重启分支，瞬时返回。** 返回值新增 `restarted` 字段，`SettingsModal.jsx` 据此显示「已保存（无需重启，即时生效）」或「已保存并重启」。

**验证**：新增 `scripts/test-api-server-stop.js`（对比旧/新逻辑 × 空闲连接/in-flight/无连接三种状态）。
真实运行时（Electron 28.3.3 / Node 18.18.2）**7/7 通过**：
- 旧逻辑：空闲连接 **挂住 >2512ms 不关闭**（诊断输出 `服务器侧连接数=1, agent 空闲 socket=1`）；in-flight 同样挂住。
- 新逻辑：空闲连接 <600ms 关闭；in-flight 落在 2000~3000ms 宽限窗口；无连接 <200ms。

**出包**：`NODE_OPTIONS= node scripts/build-all.js --pc`（37.9 秒，版本保持 1.3.7 —— master 明确说不再升版本）。产物 `release/myGal Setup 1.3.7.exe`（160,598,217 B）+ `latest.yml`(1.3.7) + `win-unpacked/`。
asar 字节精确校验：`closeIdleConnections`/`closeAllConnections`/`API_STOP_GRACE_MS`/`needsRestart`/`restarted: false|true` 均在；PC 前端 bundle 也确为新构建（新文案「无需重启，即时生效」命中 4 次、`result.restarted === false` 命中 1 次）；**旧 `stopApiServer` 代码块残留精确计数 = 0**（彻底替换）。**安卓端本轮不用重打**（只改 PC 端）。
